# MetaAgent 编排树本地优先调研与改造方案

## 0. 这份文档回答什么

这份文档主要回答 4 个问题：

1. 现在仓库主 `chat` 到底已经能调多少本地能力，是否值得先用它打通本地编排树。
2. 原仓库已有的 `workflow` 是什么，它的原理、能力边界、可复用价值是什么。
3. 编排树接下来怎么和 `chat` 深度整合，而不是做成一个孤立页面。
4. 基于《MetaAgent_V3_产品书》和《MetaAgent_三天冲刺_安卓开发计划》，安卓本地优先阶段，编排树最少要适配哪些功能。

结论先说：

- 先打通 **安卓本地编排树调度** 是对的，这和产品书“先用成熟方案夯实稳定可演示核心闭环”的原则一致。
- 原仓库的 `chat + tool + workflow + AutoGLM/UI 子代理` 已经很强，足够支撑本地 MVP。
- 当前 `core/plan` 已经能跑，但还更像“**带依赖的任务列表**”，不是完整的“可条件分支、可提取中间结果、可候选路由加权”的编排引擎。
- 最优策略不是推翻重写，而是：**借 workflow 的执行原理，保留 plan tree 的用户可视化体验**。

---

## 1. 产品书对编排树的真实要求

根据 [MetaAgent_V3_产品书](./MetaAgent_V3_产品书.md) 的设计，编排树不是一个可有可无的附属功能，而是“做”这一条主线的中枢能力。

产品书对编排树的要求可以归纳为 6 点：

1. **先规划，再执行**  
   不是一步走一步，而是先给出一棵用户可理解的计划树。

2. **用户可控**  
   用户可以审批、修改、砍分支、调优先级，不是黑盒自动跑完。

3. **进度透明**  
   执行过程不是黑箱，手机端要能实时看节点状态和进度。

4. **异步双线程**  
   后台任务执行时，前台仍然能继续对话、插话、改方向。

5. **跨端执行**  
   手机是主入口，PC 是高性能执行臂；但移动端也必须有一个本地可演示的 MVP。

6. **动态重规划**  
   节点失败、用户改方向、环境变化时，系统应重规划，而不是整棵树报废。

这意味着你们最终要做的，不是一个“树形 UI”，而是一个：

- 用户可见
- 用户可控
- 可执行
- 可打断
- 可重规划
- 可跨设备扩展

的任务编排系统。

---

## 2. 为什么先做安卓本地编排树是对的

### 2.1 产品书允许这个顺序

产品书和三天冲刺计划都强调：

- 复赛优先用成熟方案
- 先把核心闭环跑通
- 先 Mock / 本地跑通，再替换为 PC 真链路

这和“先本地调通编排树 -> 再接 PC 节点”完全一致。

### 2.2 本地仓库已经有足够多的执行底座

当前安卓仓库并不是一个“只有聊天 UI”的项目，它已经具备很强的本地执行能力：

- 多模型聊天与 Prompt 路由
- 统一工具系统 `AIToolHandler`
- UI 自动化 / AutoGLM / PhoneAgent
- 文件系统 / HTTP / Intent / Shell / 终端
- `workflow` 执行器和调度器
- Memory / RAG / ObjectBox

也就是说，**它本来就接近一个本地 Agent 容器**。

所以本地优先不是“降级方案”，而是正确的迭代顺序：

1. 先证明“编排树真的能驱动执行”
2. 再把执行端从安卓本地扩展到 PC

### 2.3 当前 chat 本来就能调用很多功能

这一点是明确的。

从 `ToolRegistration.kt` 可以看到，主 `chat` 所依赖的工具系统已经注册了大量本地能力，包括但不限于：

- `visit_web`
- `http_request`
- `execute_intent`
- `open_file`
- `list_installed_apps`
- `run_ui_subagent`

这说明仓库原本的聊天系统，已经不仅是“文本聊天”，而是“**可工具调用的聊天容器**”。

所以编排树最应该做的，是**复用这些能力并把它们组织成任务节点**，而不是另起一套平行宇宙执行器。

## 3. 当前编排树现状：已经能跑，但还偏“任务列表”

### 3.1 已经具备的部分

当前 `core/plan` 已经有这些能力：

- `PlanNode` / `TaskSession` / `TaskEvent` 模型层
- `PlanTreeGenerator` 生成计划
- `PlanTreeExecutor` 执行计划
- `PlanTreeCard` / `PlanTreePanel` / `TaskProgressBar` UI
- 审批 / 暂停 / 恢复 / 取消 / 清除
- 节点失败后的重规划

并且现在已经接入了本地执行：

- `CHAT`
- `CLI`
- `ANDROID`

这意味着现在的编排树已经是一个**可执行的本地任务树 MVP**。

### 3.2 当前最大问题：更像 DAG 列表，不像完整编排引擎

虽然名字叫 Plan Tree，但现在的运行方式更接近：

- 一组 `PlanNode`
- 每个节点有 `dependsOn`
- 执行器每次找“下一个可执行节点”

这没有问题，但它还缺少完整编排引擎的几个核心维度：

1. **没有显式条件节点**
   不能表达“如果找到歌曲就继续，否则换路线”。

2. **没有显式逻辑节点**
   不能表达“多个前置结果 AND / OR 后再决定下一步”。

3. **没有显式提取节点**
   不能把前面搜索结果里的关键信息抽出来，供后续节点引用。

4. **没有参数引用**
   后续节点不能自然地引用前置节点输出，而不是只靠自然语言描述。

5. **没有候选路径加权**
   当前是模型先给一条路径，不是运行时多方案评分择优。

6. **没有 workflow 复用层**
   仓库已有 workflow 引擎，但 plan tree 还没有把它纳入执行面。

所以当前编排树可用，但还不够“聪明”。

## 4. 原仓库 `workflow` 是什么：详细原理

`workflow` 是原仓库早就有的一套**静态流程引擎**，它和 plan tree 不是一回事，但非常值得复用。

### 4.1 数据模型是什么

`Workflow.kt` 里定义了完整的流程图模型：

- `Workflow`
- `WorkflowNode`
- `TriggerNode`
- `ExecuteNode`
- `ConditionNode`
- `LogicNode`
- `ExtractNode`
- `WorkflowNodeConnection`

这意味着它本质上不是“单链表流程”，而是一个支持图结构的工作流。

### 4.2 每类节点是做什么的

#### `TriggerNode`

触发节点，表示工作流从哪里启动。

触发方式支持：

- `manual`
- `schedule`
- `event`

#### `ExecuteNode`

执行节点，作用是“调一个工具”。

它有两个关键字段：

- `actionType`
  - 工具名，比如 `http_request`、`list_files`、`click_element`
- `actionConfig`
  - 工具参数，可以是静态值，也可以引用其他节点输出

这是 workflow 最重要的地方：**它不是抽象描述，而是已经能落到具体工具调用了。**

#### `ConditionNode`

条件判断节点。

支持的操作包括：

- `EQ`
- `NE`
- `GT`
- `GTE`
- `LT`
- `LTE`
- `CONTAINS`
- `NOT_CONTAINS`
- `IN`
- `NOT_IN`

#### `LogicNode`

逻辑汇总节点，支持：

- `AND`
- `OR`

它可以把多个前置结果汇总成一个布尔判断。

#### `ExtractNode`

提取节点，非常关键。

支持：

- `REGEX`
- `JSON`
- `SUB`
- `CONCAT`
- `RANDOM_INT`
- `RANDOM_STRING`

它的价值在于：**前面节点的输出可以结构化提取，再喂给后面节点**。

这正是你举的“先搜索歌曲 -> 提取歌名/链接 -> 再打开网易云”的基础能力。

### 4.3 执行原理是什么

`WorkflowExecutor.kt` 的核心思路不是“顺序 forEach”，而是**依赖图 + 拓扑执行**。

原理可以概括成这几步：

1. 构建依赖图
   - 节点连接关系来自 `connections`
   - 节点参数里的 `NodeReference` 也会形成隐式依赖

2. 计算每个节点入度

3. 从入度为 0 的节点开始执行

4. 每执行完一个节点，就减少后继节点入度

5. 入度归零的节点进入队列，继续执行

这就是一个标准的 DAG 拓扑执行器。

### 4.4 它怎么处理分支

它不是简单 `if`，而是：

- `ConditionNode` 先计算真假
- `LogicNode` 汇总多个真假
- `Connection.condition` 决定后继边是否激活

这意味着它已经能表达：

- 成功分支
- 失败分支
- 正常分支
- 条件不满足则跳过

### 4.5 它怎么执行工具

workflow 最关键的价值在于：最终执行时会构造 `AITool`，然后直接调用：

- `toolHandler.executeTool(tool)`

也就是说，workflow 已经天然复用了整个主仓的工具生态。

### 4.6 它还能调度吗

可以。

`WorkflowScheduler.kt` 里有 `scheduleWorkflow()`，说明 workflow 不只是手动点击执行，也支持定时和后台调度。

### 4.7 workflow 的优点

workflow 现成具备这些强项：

- 条件分支
- 逻辑判断
- 参数引用
- 结果提取
- 拓扑执行
- 工具直接调用
- 调度器支持

### 4.8 workflow 的弱点

它也有明显局限：

1. **是静态流程**
   - 通常是人提前配置好，不是 AI 运行时现拆。

2. **用户不可见性不够强**
   - 它不是天然为“用户审批 + 任务共做 + 实时解释”设计的。

3. **陪伴感弱**
   - 更像自动化流程，不像 Copilot 共做任务树。

4. **跨端语义没有直接做**
   - 它是本地工具流，不是手机主控 + PC 子代理架构。

所以 workflow 不该取代 plan tree，而应该成为 plan tree 的底层能力来源之一。

## 5. 应不应该“抄 workflow”

答案是：**应该借原理，不应该直接照搬 UI 和产品形态。**

### 5.1 不应该直接照搬的部分

不建议把编排树直接做成 workflow 编辑器，因为：

- 用户不想看一堆工程化节点类型
- 评委要的是“AI 共做任务树”，不是“低代码流程图平台”
- 你们产品书强调的是“陪伴式任务推进”，不是“自动化平台”

### 5.2 必须借鉴的部分

但 workflow 的这些执行原理，plan tree 非借不可：

1. 依赖图与拓扑执行
2. 条件节点
3. 逻辑节点
4. 提取节点
5. 参数引用
6. 工具级调用
7. 失败分支处理

一句话概括：

> **plan tree 负责“给用户看”，workflow 原理负责“让它真的能跑复杂逻辑”。**

## 6. 编排树应该怎么整合到 chat

### 6.1 正确定位

编排树不应该是一个单独的功能页，而应该是 `chat` 的一种“任务模式”。

因为产品书里的交互方式本来就是：

- 用户先对手机说目标
- 系统识别为复杂任务
- 进入 Agent / Plan Tree 模式
- 用户审批
- 后台执行
- 前台继续聊天

这说明 **chat 才是主入口，plan tree 是 chat 的一种工作形态**。

### 6.2 建议的整合方式

建议分 3 层：

#### 第一层：普通对话层

用户问简单问题时，走普通 chat。

#### 第二层：任务识别层

当输入满足这些条件时，切到编排树模式：

- 明显是多步骤目标
- 明显需要工具
- 明显有执行意图
- 明显需要持续推进

例如：

- “帮我完成 CNN 实验”
- “帮我整理这门课资料并出复习卡”
- “打开网易云，找首适合夜跑的歌并播放”

#### 第三层：任务执行层

进入 plan tree 后：

- 聊天区继续可用
- 顶部显示任务进度条
- 中间可切 plan panel
- 执行日志持续回流

### 6.3 当前代码已经到哪一步

现在已经做到：

- `AIChatScreen` 集成了 `PlanTreePanel`
- `ChatViewModel` 集成了 `PlanTreeExecutor`
- 任务面板里可输入目标创建计划

但还没做到：

- 普通聊天输入自动识别并转 `createPlanFromGoal()`

所以现在的整合是“半整合”：

- UI 已经进 chat
- 入口还没完全进 chat 主输入流

### 6.4 下一步建议

下一步最值得做的不是继续堆页面，而是：

1. 在 chat 主发送链路里加“复杂任务识别”
2. 命中时直接触发编排树生成
3. 生成后把计划卡片插入消息流
4. 继续保留右上角编排树面板作为任务详情页

这样编排树才真正成为 chat 的一种工作模式。

## 7. 基于任务书，编排树最少要适配哪些功能

这里说的是 **安卓本地优先阶段的最小适配面**，不是最终完整版。

### 7.1 必选 1：`CHAT` 节点

作用：

- 分析
- 解释
- 汇总
- 给建议
- 结果回报

这是所有任务的兜底能力。

没有它，编排树就只剩工具调用，没有“学伴感”。

### 7.2 必选 2：`ANDROID_UI` 节点

作用：

- 打开 App
- 页面导航
- 自动点击
- 自动输入
- 完成手机端任务

这个直接对应产品书里的：

- 手机主入口
- 手机端操作
- 共做体验

并且也最符合你举的网易云例子。

对应底座：

- `run_ui_subagent`
- `PhoneAgent`
- AutoGLM/UI 自动化

### 7.3 必选 3：`WEB/HTTP_SEARCH` 节点

作用：

- 搜网页
- 查资料
- 访问链接
- 调接口

原因：

- 产品书里的很多学习任务，本质上都需要联网检索
- 你举的“先搜热门歌曲，再决定播放什么”也需要它

这块当前仓库已有工具：

- `visit_web`
- `http_request`

但当前 plan tree 还没把它适配进执行层，因此它是下一阶段最优先补的能力之一。

### 7.4 必选 4：`INTENT / APP_OPEN` 节点

作用：

- 直接打开应用
- 打开指定页面
- 跳系统设置

原因：

- 纯 UI 子代理不是最优路径
- 有些动作直接用 Intent 更稳、更快

这也是“动态选择最优路径”的关键候选执行方式之一。

### 7.5 必选 5：`CLI / LOCAL_RUNNER` 节点

作用：

- 检查工作区
- 调试本地环境
- 做简单命令执行

原因：

- 你现在的本地 MVP 已经在用它
- 产品书“下午实验课 / CNN 实验”场景也很适合有这类节点

即使最终 PC 会承接大部分 CLI，这个节点在本地 MVP 阶段仍然有价值。

### 7.6 必选 6：`WORKFLOW` 节点

这不是产品直接感知的功能，但从技术角度，我认为它应该尽快进入最小适配面。

原因很简单：

- 主仓已经有大量 workflow 基础设施
- 不可能把所有工具都一个个硬接到 plan tree
- 最合理的方式是：**plan tree 的某些节点，直接触发一个已有 workflow**

这样你们可以把复杂多步本地能力，先沉淀成 workflow，再让 plan tree 进行更高层编排。

### 7.7 必选 7：审批 / 重规划 / 中途变向

这不是某个工具节点，而是整个编排树的灵魂能力。

至少要支持：

- 计划审批
- 驳回重规划
- 失败重规划
- 用户中途改方向

否则就会退化成“另一个自动任务跑批器”，而不是产品书里的 Copilot 共做系统。

## 8. 你举的网易云例子，未来正确的编排方式是什么

目标：

> 去网易云点赞一首歌。  
> 可以先搜索热门歌曲，再调用 UI 自动化进入网易云播放/点赞，最后输出结果。

这个目标如果用“升级后的 plan tree + workflow 原理”来做，理想结构应该是：

### 路径 A：搜索后再操作

1. `CHAT` 节点：理解用户意图，确定筛选条件  
2. `WEB_SEARCH` 节点：搜热门歌曲 / 候选歌单  
3. `EXTRACT` 节点：提取歌名、歌手、链接或关键词  
4. `DECISION` 节点：决定最适合的目标歌曲  
5. `INTENT` 节点：打开网易云  
6. `ANDROID_UI` 节点：搜索歌曲、进入页面、点赞  
7. `CHAT` 节点：总结结果并回复用户

### 路径 B：直接走 App

1. `INTENT` 节点：打开网易云
2. `ANDROID_UI` 节点：进入热门榜单
3. `ANDROID_UI` 节点：选择歌曲并点赞
4. `CHAT` 节点：总结结果

### 真正的“动态选择最优路径”是什么

不是只让模型生成一条路径，而应该是：

- 候选路径 A：先 Web 搜，再进 App
- 候选路径 B：直接进 App 榜单
- 候选路径 C：如果有 API / Intent 能力，优先更稳路径

然后依据这些因素打分：

- 当前工具可用性
- 是否已安装网易云
- 权限是否具备
- UI 自动化成功率
- 搜索成本
- 用户是否指定“热门歌曲”

当前 plan tree **还没有这个显式加权层**，但 workflow 的条件/逻辑/提取能力，是做这个加权层的基础。

## 9. 建议的技术路线：不要重写，要分层升级

### Phase A：本地 MVP 已有基础上继续补

目标：

- `CHAT`
- `CLI`
- `ANDROID`
- `WEB/HTTP`
- `INTENT`

做到“本地主要任务可跑”。

### Phase B：把 workflow 纳入 plan tree 执行面

新增一种 plan node：

- `WORKFLOW`

语义是：

- 这个节点不直接跑工具
- 而是调用一个现有 workflow

这样可以迅速扩大 plan tree 的能力面。

### Phase C：给 plan tree 增加 workflow 原理

重点不是复制 workflow UI，而是把这些原理加进去：

- 条件节点
- 逻辑节点
- 提取节点
- 参数引用
- 候选路由打分

### Phase D：接入 PC 节点

当本地执行面稳住后，再新增：

- `PC_CLAUDE`
- `PC_CLI`
- `PC_BROWSER`

这时安卓仍然是主调度和主可视化端，PC 只是执行臂。

## 10. 最终建议

### 建议一

先坚持“安卓本地优先”完全正确，不要急着把所有精力切到 PC。

### 建议二

当前 plan tree 不要继续按“列表 + adapter 枚举”硬扩太多，而要开始吸收 workflow 的执行原理。

### 建议三

workflow 不应该和 plan tree 竞争，而应该成为 plan tree 的底层执行能力库。

### 建议四

编排树下一阶段最该补的能力不是更多 UI，而是：

1. `WEB/HTTP_SEARCH`
2. `INTENT`
3. `WORKFLOW`
4. chat 主输入自动触发 plan tree

### 建议五

真正的“模型自己决定走哪条路”，不是今天这版就已经完成，而是下一阶段要补的高级能力。  
今天这版只能说：

- 模型能决定节点顺序和 adapter 大类
- 失败后能重规划

但还没有做到：

- 多候选路径加权择优
- 工具级最优路由
- 实时环境感知后自适应切换

---

## 11. 一句话结论

> **编排树应该继续以 chat 为主入口，以用户可见任务树为外层体验；执行内核则逐步吸收 workflow 的图执行、条件分支、提取和工具调用能力。**

这样做，既不会失去产品书里的“共做感”，也不会浪费原仓库已经非常成熟的 workflow 底座。
